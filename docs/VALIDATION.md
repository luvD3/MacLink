### 0.1.1 延迟诊断

用户补充主要症状为“鼠标操作后，画面明显晚一拍”。只读检查得到：

- Windows 到 Mac 为直接局域网路由；Wi-Fi 6 / 5 GHz，链路协商接收 961 Mbps、发送 1081 Mbps。
  10 次 ping 全部成功，中位数 2 ms、最大 33 ms；网卡错误和丢弃为 0。链路速率不是实际传输吞吐量。
- GPU 加速正常；样本中的 React 布局、样式重算为 0，没有工具栏动画或模糊层持续绘制。
- 实际画面仍为 3840×2160，使用 ZRLE。大区域更新的同步解码与写入 canvas 平均约 89 ms，
  等待数据/事件处理约 71 ms，合计约 160 ms。等待不是纯网络延迟，采样也不是端到端输入延迟测试。
- 临时 compression=0 相比 6 未显示有效改善。临时移除 ZRLE 后服务端改用 Zlib，
  大区域处理均值约 172 ms，也没有改善。全部诊断 wrapper、编码列表及 compression=6 已恢复。
- 服务端未提供标准的远程改尺寸或持续更新能力；公开的 resizeSession 不能替代 Mac 显示设置。

当时用户选择 2560×1440 做后续对照，但暂时不方便修改 Mac。界面控制工具亦无法启动
（kernel assets 路径错误），因此**尚未更改分辨率，也未完成 1440p 对照测试**。
截至上述 0.1.1 诊断结束，4K 延迟仍未达到用户的验收标准。此后用户明确要求保留 Mac 的 4K 分辨率，
转为优化客户端解码；0.1.2 的合成基准与后续实机结果见下文。
未来测试应核对实际接收的 framebuffer 尺寸，避免把 HiDPI 文字缩放误当作减少传输像素。
诊断统计保存在 ignored 的 test-results 目录，仅作本次排查依据；不同场景样本不作为帧率或改善百分比承诺。

### 0.1.2 解码基准

2026-10-29 在本机 Windows x64、Electron 45.1.0 / Chromium 156.0.8078.49 中测试。
客户端采用 WASM 解压及批量像素展开；**Mac 分辨率未修改，目标画面仍为 3840×2160**。

基准使用确定性的合成 ZRLE 数据，不读取真实桌面。每组包含 3 个共享 zlib 字典的完整 4K 矩形；
混合组覆盖 raw、solid、2/4/16 色 packed palette、plain RLE 和 palette RLE，Raw 组全部使用
ZRLE 的 raw 子编码。另用 65×67 矩形检查边缘 tile、非零坐标及跨矩形字典。
每方案预热 2 轮、测量 10 轮，共 30 个矩形；按轮交替运行各方案。使用实际 noVNC Display 和 Canvas，
计时包括解压、像素展开、Canvas 命令提交及 flip，编译、构造实例和画面读取在计时外。

| 合成内容 | 原始 noVNC p50 / p95 | 仅 WASM p50 / p95 | WASM + 像素展开优化 p50 / p95 |
| --- | --- | --- | --- |
| 4K 混合 | 147.7 / 158.0 ms | 69.2 / 74.3 ms | 32.3 / 34.7 ms |
| 4K Raw 子编码 | 231.0 / 243.4 ms | 120.2 / 125.0 ms | 115.0 / 118.9 ms |

平均耗时分别从 149.30 降至 32.61 ms、从 232.54 降至 115.45 ms，即相对原版降低 78.2% 和 50.4%。
相对仅 WASM，像素展开优化额外降低 53.0% 和 4.4%。每组均通过 68 项独立 RGBA 哈希检查，
并在计时结束后通过 4 项真实 Canvas 输出哈希检查。

这些数字仅表示本机合成数据的渲染线程耗时，**不包含 Mac 捕获、网络等待、GPU 完成或端到端输入延迟**，

### 0.1.2 实机编码取舍

2026-10-29，用户提出增加局域网传输量以减轻解码压力。保持同一条 3840×2160 Mac 连接，
依次请求默认编码、Hextile/Raw、Raw，再恢复默认。每阶段主动请求 3 次完整刷新，
只记录字节数和耗时，不采集桌面内容或凭据，也不发送键鼠输入。已确认实际使用 WASM 和批量像素展开。

| 请求方式 / 实际选择 | 完整 4K 矩形同步处理均值 | 完整刷新请求至 Canvas 提交均值 |
| --- | --- | --- |
| 默认 / ZRLE | 62.5 ms | 274.2 ms |
| Hextile 优先 / Raw | 33.4 ms | 1086.3 ms |
| Raw / Raw | 33.7 ms | 1069.3 ms |
| 恢复默认 / ZRLE | 62.7 ms | 271.3 ms |

Raw 确实降低了解码与绘制的同步开销，但每个完整 4K 帧约 31.6 MiB，
本次接收与处理总时长超过 1 秒。数据送达耗时超过节省的解码时间；这不能单独区分无线链路、
Mac 的发送实现与主机接收路径的影响。请求 Hextile 后观察到 Raw，不能据此断言 Mac 完全不支持 Hextile。

随后对照压缩级别 6、1、0、恢复 6，各 3 次完整刷新，均使用 ZRLE。
刷新均值分别约 310.9、302.6、285.8、292.1 ms，完整矩形同步处理均约 60–62 ms；
没有稳定的延迟或流量改善证据，不能确认此 Mac 按压缩级别提示改变了编码。
所有偏好和诊断包装均已恢复，当前继续使用默认编码顺序与压缩级别 6。

该测量包括服务端响应、数据到达和客户端处理，但不包含显示器最终呈现，也不是鼠标到画面的端到端延迟。
背景画面可能变化，样本数有限，不据此推算实际交互 FPS。
复现脚本为 `scripts/encoding-check.mjs`；压缩对照使用 `node scripts/encoding-check.mjs <CDP端口> --compression`。
原始统计位于 `test-results/live-encodings.json` 和 `test-results/live-compression.json`。

### 0.1.3 剩余等待的分解

旧编码对照同时存在手动完整刷新和 noVNC 自动增量请求，约 274 ms 的结果可能包含先前增量更新，
不能归因为单个请求的纯服务端响应。后续使用 `scripts/latency-check.mjs` 屏蔽当前连接的自动增量请求，
先完整刷新预热，再等待最多 3 秒以确认连续 500 ms 没有 FBU 完成、接收队列和显示队列为空。
之后串行请求 5 次完整 4K 刷新，以接收字节区间关联覆盖至少 95% 画面的 FBU，保留未匹配更新的元信息。
结束后恢复全部包装并补发正常增量请求，不读取桌面像素、压缩内容或发送键鼠输入。

前台窗口的 5 个样本均值如下，报告为 `test-results/live-latency-foreground.json`：

| 可观察阶段 | 均值 |
| --- | --- |
| 发出完整刷新请求 → 目标 FBU 的首个 WebSocket 数据 | 159.22 ms |
| 目标 FBU 首批 → 末批 WebSocket 数据到达 | 88.82 ms |
| 数据齐备后的 ZRLE 解码及同步 Canvas 写入 | 45.88 ms |
| display.flip 返回 → 后续第二次 rAF 回调 | 9.36 ms |

首包前等待包含服务端捕获、编码、请求调度及传输等环节；数据到达跨度也不能直接称为纯网络延迟。
两次 rAF 只是浏览器回调边界，不证明 GPU 已完成或显示器已经呈现；主动完整刷新亦不是鼠标到画面的延迟。

主进程采样与更早一轮 renderer 测量同步，**并非上表前台测量的同期数据**。
那一轮 5 个样本中，请求到首个 TCP 数据均值为 165.04 ms；TCP 数据到达跨度为 92.45 ms，
renderer 观察到的 WebSocket 跨度为 92.66 ms。桥接发送回调延迟 p95 为 0.206 ms、最大 0.344 ms，
WebSocket 最大待发送队列为 0，TCP 暂停次数为 0。该样本没有显示本机桥接积压；不能由此把全部剩余时间归给网络。
原始数据为 `test-results/main-transport-profile.json` 与 `test-results/live-latency.json`。

更早一轮中，窗口最小化造成 rAF 未在 500 ms 上限内完成；即使 DOM 的 visibility/focus 仍报告可见和聚焦，
也不能把此超时算作实际交互延迟。恢复窗口后重新采样，flip 到第二次 rAF 均值约 9 ms。
本轮没有修改 `backgroundThrottling`。

### 0.1.3 受控请求调度对照

`scripts/pipeline-refresh-check.mjs` 在相同 3840×2160 连接上执行“串行 → 提前一个请求 → 恢复串行”。
屏蔽自动增量请求，三段都只主动请求完整画面；提前模式在当前完整 FBU 头已可解析且矩形数非零时发送下一次请求，
始终最多保留一个后续请求。每段丢弃首帧预热后计算完成间隔，段间排空，结束在 FBU 边界恢复并补发正常增量请求。

| 对照轮次 / 指标 | 串行 | 提前一个请求 | 恢复串行 |
| --- | --- | --- | --- |
| 首轮，每段 8 帧：中位完成间隔 | 367.3 ms | 333.8 ms | 448.1 ms |
| 首轮，每段 8 帧：p95 完成间隔 | 384.3 ms | 454.3 ms | 464.9 ms |
| 复测，每段 12 帧：中位完成间隔 | 447.7 ms | 393.6 ms | 419.4 ms |
| 复测，每段 12 帧：p95 完成间隔 | 552.4 ms | 485.4 ms | 521.6 ms |

复测严格发送并收到 37 次完整刷新：排空预热 1 次，加三段各 12 次；每段再丢弃第一帧，
保留 11 帧及其间的 10 个完成间隔。三段接收字节量各约 22.837 MB（十进制），相差小于 0.01%，
每段结束均无未完成的完整刷新请求。原始报告为 `test-results/live-pipeline-refresh-first.json` 与
`test-results/live-pipeline-refresh.json`。

两轮提前请求的中位间隔均低于同轮两个串行阶段；首轮 p95 未优于起始串行阶段，也能看到阶段间漂移。

0.1.3 默认启用 `PipelinedRFB`：仅把**一个增量更新请求**提前到当前 FBU 头就绪时发送，
以重叠下一次服务端更新与当前接收、解码过程。48 行子类继续使用 noVNC 的消息和矩形解析；
启用持续更新、显示有背压或等待远端改尺寸时保留原调度，实际尺寸变化后修正请求范围并在本次连接回退。
没有修改 Mac 的 4K 分辨率、编码/画质偏好或远端设置。用户随后反馈 0.1.3“我感觉是可用了”；
这是主观交互反馈，长时间运行仍待完成。

### 0.1.3 正常增量更新核对

2026-10-29 对现有连接被动采样 15 秒，没有主动刷新、发送输入或采集桌面内容。
画面保持 3840×2160；观察到 292 个增量请求、0 个完整刷新请求，以及 292 个 74×50 的 ZRLE 矩形。
单个矩形为 3,700 像素，约占整屏的 0.045%；同期 WebSocket 接收载荷合计 105,114 字节，约 7 KB/s。
这是采样期间实际更新的元信息，未核实用户当时是否正在打字，不能据此报告打字延迟。
原始统计位于 `test-results/live-incremental.json`。

代码核对同样确认：首屏初始化请求完整画面，正常会话的请求均为 `incremental=true`。
请求的全屏范围表示监听整个屏幕的变化，不要求每次重传整屏。noVNC 保留背面画布，

网络更新矩形的粒度由 Mac 服务端决定；此前受控完整刷新对照与正常增量会话应分开解读。

### 真实交互与拖动对照

2026-10-29 使用 0.1.3 在同一条 3840×2160 Mac 连接上发送受控 CDP 输入，
通过避开插入光标的字符 ROI 哈希、滚动区域哈希及拖动时的红色标记质心，核对输入对应的画面变化。
`eventToFlipMs` 从 DOM 事件时间戳计到对应 Canvas `flip` 返回，采用修正后的 `flip.endAt`；
它不是物理输入到显示器发光的延迟。完整口径、各阶段数据及本地诊断说明见
[真实交互延迟记录](INTERACTION-LATENCY.md)。

默认提前请求 A/B 两批各有 20 次单键编辑操作，每批包含 10 次字符输入和 10 次删除；
混合编辑的中位数分别为 113.2 / 107.4 ms。只合并其中 20 次字符输入时，
事件到 flip 的 p50 / p95 为 123.7 / 171.6 ms，同步解码/写入 p50 为 0.2 ms。
滚动 A/B 各有 20 次单次 wheel，合并 40 次的 p50 / p95 为 170.9 / 363.3 ms，最大 537.3 ms，
同步解码/写入 p50 为 7.4 ms。中间串行阶段没有证明滚动能从提前请求稳定受益；本轮不扩大性能保证。

有效拖窗对照按 17 ms → 临时 8 ms → 恢复 17 ms 执行，每段包含 8 次连续拖动、320 次移动，
分别匹配到 91 / 101 / 95 个可见位置；这些位置不是独立输入试验。
事件到 flip 的 p50 为 106.0 / 94.8 / 103.3 ms，p95 为 171.0 / 150.9 / 153.3 ms，
同步解码/写入均值约 14–16 ms；三段指针发送均为 321 次，含最后一次释放。
这一轮中位数改善约 8–11 ms，支持 0.1.4 仅缩短按键拖动的合并间隔，
不能宣称打字、滚动或所有拖动尾部卡顿也会改善。未实际移动窗口的初批拖动数据已作废。

ROI 读回在该次 flip 后进行，字符输入约 1.4 ms、滚动约 10–11 ms、拖动约 13–14 ms，
会扰动后续处理，不能机械扣除。网络另采样约 30 秒、150 包，无丢包，RTT p50 / p95 / 最大值为 1 / 8 / 73 ms；
该时段与最终纳入的交互批次不重叠，且 ICMP 不能代表 RFB 端到端延迟。
现有证据把多数等待定位在相关更新数据交付之前，尚不能拆成 Mac 编码或纯网络耗时。

本轮没有保存桌面内容或凭据，没有更改 Mac 分辨率。临时 TextEdit 文档已关闭并丢弃，
诊断包装已恢复，没有持久远端改动。0.1.4 的实现仅由这轮临时实机实验支持，
其打包程序的持续运行与用户主观复验仍需另行记录。

## 发布步骤

1. 执行类型检查、单元测试和 Electron 集成测试。
2. 运行 `npm run make`，确认 ZIP 中包含程序和第三方许可。
3. 在干净的 Windows 用户目录启动程序；保存连接、退出重启、确认配置保留且没有密码。
4. 执行已支持 macOS 版本的实机清单，记录未验证项。
5. 首版使用手动解压更新；后续升级需要保持连接配置兼容。
