# 真实交互延迟记录

2026-10-29，在同一条真实 Mac 连接上测量单键编辑、单次滚轮和连续拖窗。
客户端为 0.1.3，Mac framebuffer 始终为 **3840×2160**，使用现有 ZRLE、WASM 解压和增量更新管线。
本轮采样时尚未核实系统版本；后续确认这台设备为 macOS Sequoia 15.8.2，不扩大到其他版本的兼容结论。

本轮发现，字符输入及滚动的大部分等待发生在相关更新数据送达之前；同步解码与 Canvas 写入并非主要耗时。
临时把拖动时的鼠标移动合并间隔从 17 ms 改为 8 ms，三段对照的中位结果改善约 8–11 ms。
这支持 0.1.4 仅缩短按住鼠标按钮拖动时的合并间隔，不能据此承诺打字、滚动或其他桌面的延迟也会降低。

## 测量定义与限制

`eventToFlipMs` 从受控 CDP 输入产生的 DOM 事件 `event.timeStamp`，计到对应 `display.flip()` 返回。
汇总采用修正后的 `flip.endAt`，拖动采用 `flipEndAt`。起点包括事件进入 DOM 处理器之前的排队，
但不是物理键盘、鼠标的硬件时间；终点是 Canvas 命令提交边界，不是 GPU 完成或显示器发光时刻。
报告里的后续 rAF 回调也不证明显示器已呈现。

视觉对应关系通过受控内容和位置核对：

- 单键编辑使用 26×42 像素的字符区域，在输入和删除前取得基线哈希，排除插入光标闪烁区域。
- 滚动使用 128×64 像素的文本区域，每次输入前建立基线，再关联发生变化的更新。
- 拖窗使用 128×28 像素区域的红色标记质心，将实际窗口位置与已发送的指针位置匹配，允许最多 1.1 个远端像素的误差。

哈希变化本身不是任意桌面内容下的因果证明；本轮依赖已核对的测试内容、交替动作和位置轨迹。
不同输入可能被服务端合并，不能把连续拖动中的每个可见位置当作独立输入样本。
探针只保存时间、计数、区域尺寸、哈希与质心等统计，不保存桌面截图、像素数组、文档内容或凭据。

ROI 读取在该次 `flip` 返回后发生。字符输入的读回均值约 1.4 ms，滚动约 10–11 ms，拖动约 13–14 ms。
这些耗时不计入该次 `eventToFlipMs`，但会占用主线程并影响后续事件和更新；不能从测量值中机械扣除。
`decodeCpuMs` 是矩形解码及同步 Canvas 写入的墙钟耗时，不是整机 CPU 利用率。

分位数沿用汇总脚本：p50 取排序后索引 `floor(n / 2)` 的值，p95 取最近秩，不做插值。
各阶段分位数独立计算，不能用它们相减或相加拼出同一条样本的完整耗时。

## 单键编辑与滚动

两类操作均按“提前请求 A → 临时串行 → 恢复提前请求 B”执行；其他解码和显示设置保持不变。
提前请求使用 0.1.3 原有管线，串行阶段仅临时关闭提前请求。
每批包含 20 次操作，动作间等待约 850 ms；均观察到对应区域变化。

单键编辑每批是 **10 次字符 `0` 输入和 10 次删除**，因此默认 A/B 两批共 40 次编辑操作，
其中纯字符输入只有 20 次。滚动每批为 10 次向上、10 次向下的单次 wheel，默认 A/B 共 40 次。
这里的单次 wheel 是受控浏览器输入，不代表物理滚轮或触控板的所有事件形式。

| 默认提前请求 A/B 汇总 | 样本数 | 事件 → flip p50 | p95 | 最大值 | 同步解码/写入 p50 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 字符 `0` 输入，仅合并 insert | 20 | 123.7 ms | 171.6 ms | 242.0 ms | 0.2 ms |
| 单次 wheel，上下方向合并 | 40 | 170.9 ms | 363.3 ms | 537.3 ms | 7.4 ms |

纯字符输入从事件到相关 FBU 首批 WebSocket 数据的均值为 131.30 ms，事件到 flip 均值为 131.63 ms，
同步解码/写入均值仅 0.18 ms。主要等待已出现在数据到达之前。
滚动两批的事件到首批数据均值分别为 152.81 / 190.43 ms，数据到达跨度均值为 5.24 / 4.53 ms，
同步解码/写入均值为 9.16 / 7.45 ms。滚动的 DOM 分发与发送也有可观察等待，
事件到发送的中位数分别为 20.6 / 22.7 ms，不能把事件到首包全部算作远端等待。

以下保留每批原始口径，单键编辑行包含输入和删除，不与上表的纯字符输入混用：

| 操作与阶段 | 样本数 | 事件 → flip p50 | p95 | 最大值 | 同步解码/写入 p50 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单键编辑：提前 A | 20 | 113.2 ms | 165.1 ms | 171.6 ms | 0.2 ms |
| 单键编辑：串行 | 20 | 118.4 ms | 276.6 ms | 307.1 ms | 0.1 ms |
| 单键编辑：提前 B | 20 | 107.4 ms | 170.2 ms | 242.0 ms | 0.2 ms |
| 滚动：提前 A | 20 | 170.6 ms | 240.1 ms | 537.3 ms | 9.2 ms |
| 滚动：串行 | 20 | 168.2 ms | 235.3 ms | 242.8 ms | 8.7 ms |
| 滚动：提前 B | 20 | 188.8 ms | 363.3 ms | 505.6 ms | 7.2 ms |

这组编辑结果与保留提前请求的方向一致，但滚动没有显示同样的改善，恢复阶段也存在漂移。
这是一次按顺序进行的有限样本对照，不是随机重复试验；不能把差值全部归因于请求调度。
结合此前受控完整刷新的结果，继续保留原管线，本轮不据此扩展为普遍的交互性能保证。

## 连续拖动：17 ms → 8 ms → 恢复 17 ms

每段按住左键，在两个方向交替拖动 8 次；每次发出 40 个受控移动，总计 320 次移动。
三段都记录到 321 次指针发送，包含最后一次释放，按钮仍按下时的发送为 320 次。
因此本轮 8 ms 实验没有增加该脚本的指针发送总数，不能据此推断其他输入速率下流量也不变。

| 阶段 | 连续拖动次数 | 匹配到的可见位置 | 事件 → flip p50 | p95 | 事件 → 发送 p50 | 同步解码/写入均值 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 默认 A，17 ms | 8 | 91 | 106.0 ms | 171.0 ms | 7.5 ms | 14.59 ms |
| 临时 8 ms | 8 | 101 | 94.8 ms | 150.9 ms | 2.4 ms | 15.82 ms |
| 恢复默认 B，17 ms | 8 | 95 | 103.3 ms | 153.3 ms | 5.1 ms | 15.17 ms |

91 / 101 / 95 是连续轨迹中匹配成功的可见位置，**不是等量的独立按键或独立拖动试验**；三段未匹配的位置记录均为空。
8 ms 阶段的事件到 flip 中位数比两侧默认阶段低 11.2 / 8.5 ms，p95 也较低。
但其最大值为 274.7 ms，高于两侧的 205.9 / 218.2 ms，且仍观察到一次长任务；不能声称所有尾部卡顿都已改善。
三段接收量分别约 16.22 / 18.31 / 17.08 MB，画面更新及时间环境并非完全相同。

三段发送到相关 FBU 首批数据的均值分别为 73.63 / 72.81 / 77.41 ms，
数据到达跨度均值为 14.64 / 10.15 / 10.59 ms。解码/写入仍约 14–16 ms，缩短合并间隔没有降低这部分成本。
这是一轮有视觉位置确认的实机实验，支持在 0.1.4 中仅对按住鼠标按钮的拖动采用 8 ms，普通悬停移动继续沿用 17 ms。
实验是在 0.1.3 会话中临时替换调度完成，不能称为已经测得 0.1.4 打包程序的同等性能；
打字和滚动也没有应用 8 ms 后的新增性能保证。

初批 `drag-default-a.json`、`drag-faster-mouse.json` 没有实际移动目标窗口，已作废，不纳入统计或优化结论。

## 网络旁证与剩余等待

ICMP 原始记录 `interaction-network.json` 覆盖 UTC 20:59:55.402–21:00:25.833，
每约 200 ms 一包，150 包全部成功：p50 1 ms、p95 8 ms、均值 3.77 ms、最大 73 ms，无丢包。
该时间段晚于上述编辑/滚动批次（UTC 20:54–20:58），早于三段有效拖动（UTC 21:01–21:03），
**与纳入结果的交互批次不重叠**，不能把某次输入尖峰与该轮 ping 直接对应。

ICMP 不是 VNC 数据路径的端到端测量，低 RTT 不能排除 TCP 排队、重传、Mac 更新调度或捕获编码等待。
当前能支持的结论是：剩余耗时多数发生在相关更新数据交付之前，而不是本轮已经测得的同步解码。
没有 Mac 端发送时序或同期传输证据，不能继续拆成“Mac 编码耗时”或“纯网络延迟”。
本轮不再盲目调整解码器，也不改为 Raw；此前完整 4K 的 Raw 对照已显示传输成本超过解码收益。
