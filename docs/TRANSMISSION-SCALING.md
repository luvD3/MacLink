# 保持 Mac 4K 的半尺寸传输

2026-10-29 实测：MacLink 可以在 **Mac 保持 3840×2160** 时接收 **1920×1080** 画面。
已测环境为 macOS Sequoia **15.8.2**、3840×2160 显示分辨率、Apple 账户认证。
半尺寸会话期间在 Mac“关于本机”中读到显示器为 3840×2160；全程没有修改显示器设置或发送 SetDesktopSize。
此结论限于这台设备和版本。

## 使用与实现

在连接编辑器或浮动工具栏的“传输”中选择“半尺寸”。4K 会变成 1080p；其他桌面同样按宽、高各一半传输，
不是任意指定一个分辨率。“适应／1:1”仍仅控制本地显示。原有连接默认保持原尺寸，偏好随连接保存，不保存密码。
工具栏显示服务器实际返回的尺寸，等待期间不把请求目标冒充实际尺寸。

Apple 的候选格式来自 [iShareScreen 的实验性协议说明 §8.10](https://github.com/renegadelink/iShareScreen/blob/main/docs/apple_vnc_rfc.md)。
它不是 Apple 官方协议文档。MacLink 自行实现十字节消息：`08 00` 后接大端 Float64，半尺寸为 `0.5`、原尺寸为 `1.0`。
实测服务器 banner 为 `RFB 003.889`，客户端仍协商标准 `003.008`，不进入 Apple 的扩展加密或虚拟显示模式。
先请求 `1.0` 验证解析仍正常，再请求 `0.5`，服务器实际返回 DesktopSize（编码 -223）1920×1080；
随后独立刷新验证收到的像素矩形覆盖整个 1920×1080。恢复 `1.0` 后也收到 3840×2160。

发现并处理了两处实机差异：

- **鼠标仍使用原始桌面坐标。** 未转换时点击“格式”会错误命中左侧“文本编辑”菜单；按实际尺寸转换后正确命中。
  先由 noVNC 处理本地缩放、视口偏移，再把传输坐标映射到原始桌面。半尺寸下一个传输像素对应两个原始像素。
- **切换尺寸后需要完整刷新。** 仅继续增量请求会留下旧尺寸的局部图像。确认新尺寸后请求一次完整画面，
  在新的像素区域覆盖整张画面之前暂停增量请求，之后恢复原有请求流水线。缩放只在完整消息边界发送。

## 延迟对照

每种操作均按 **1080p A → 4K B → 1080p C** 顺序测量；Mac 显示分辨率、画面内容和窗口位置保持不变。
数据采集使用已运行的 0.1.4，临时发送同一 Apple 缩放消息并按实际尺寸修正指针。
每次切换后先确认完整新画面，正常测量期间启用相同的增量请求流水线与 8 ms 拖动合并间隔。
本表不是打包后重新采集的 0.1.5 性能数据；正式适配器的往返切换、完整刷新和输入另做验收。

时间定义沿用 [交互延迟记录](INTERACTION-LATENCY.md)：从受控输入的 DOM `event.timeStamp` 到对应 Canvas `flip()` 返回，
**不是物理按键到显示器发光**。打字使用临时 TextEdit 文档内 36 pt 的 `0`，每批 10 次输入和 10 次删除；
滚动使用同一临时长文档，每批 20 次上下滚轮，动作间隔约 850 ms；拖窗每批 8 次往返、320 次移动和一次释放。
表中的打字仅合并真正的字符输入，删除单独保留在原始报告。

| 操作 | 4K p50 / p95 | 1080p A+C p50 / p95 | 4K / 1080p 样本数 | 同步解码和写入 p50，4K → 1080p |
| --- | ---: | ---: | ---: | ---: |
| 输入字符 | 117.4 / 199.4 ms | 147.8 / 210.3 ms | 10 / 20 | 0.2 → 0.1 ms |
| 滚动长文档 | 230.2 / 290.4 ms | 220.5 / 319.4 ms | 20 / 40 | 6.4 → 2.0 ms |
| 连续拖窗 | 88.8 / 149.0 ms | 61.0 / 101.5 ms | 106 / 245 个匹配位置 | 13.1 → 3.9 ms |

拖窗的两批 1080p 中位数分别为 60.7 和 61.6 ms，4K 为 88.8 ms；三批均没有未匹配的移动位置。
每批都是 321 条指针发送，半尺寸下视觉轨迹按 0.5 比例与原始坐标比较，最大允许误差为 0.55 个传输像素。
这些是连续运动中的相关观察，不是 245 次相互独立的实验，也不能据此推导每秒帧数。

相同动作数下，每批接收字节量（包含该批其他桌面更新，1080p 为两批均值）：

| 操作 | 4K | 1080p |
| --- | ---: | ---: |
| 20 次输入／删除 | 438,108 B | 209,909 B |
| 20 次滚动 | 2,531,543 B | 1,372,707 B |
| 8 次拖窗往返 | 13,417,588 B | 8,103,870 B |

本轮收益主要在拖窗和解码负担。输入字符的观察值反而更慢；滚动中位数只小幅下降，p95 更高，
不能宣称半尺寸普遍降低所有操作延迟。两种操作的大部分等待依然出现在相关更新数据到达之前。
本轮没有服务器侧时间戳，不能进一步把这段等待精确划分成 Mac 输入处理、画面采集、编码、网络或浏览器排队。

## 0.1.5 正式打包程序复验

重新认证后，正式程序从 ServerInit 记录原尺寸 3840×2160，自动应用已保存的半尺寸偏好，
实际收到 1920×1080；没有使用临时缩放或鼠标替换代码。通过正式工具栏执行原始→半尺寸往返，
两次都确认完整刷新覆盖归零、没有待发缩放请求、增量流水线恢复。
截图核对两种尺寸的完整桌面，无此前的局部残影。完整刷新覆盖可以跨多次 FBU 累计，重叠区域只计一次。

半尺寸下实机点击左上“文件”菜单、右下 TextEdit Dock 图标均准确命中；
新建空白临时文档，按正式鼠标实现再做八次拖动往返，101 个可见移动位置全部匹配，没有未匹配位置。
这一额外批次 p50 **56.7 ms**、p95 **112.4 ms**，同步解码和写入 p50 **4.1 ms**。
该批窗口为空白，采集时段也不同，因此不合并进前面的 A/B/A 表格。
诊断包装已恢复，空白测试文档已关闭；客户端保持半尺寸连接。

自动化通过 169 项 Vitest 检查和 13 项 E2E 流程，最后完整刷新跨 FBU 的调整重建后再次通过两项缩放 E2E。
后者分别用 100%／150% DPI 检查 fit／1:1 多点点击、视口滚动、恢复原始尺寸以及保存后重启重连。
对应本地输出为 `production-transmission.json`、`drag-production-1080.json` 及其汇总。

## 测量限制和数据

探针从独立小 Canvas 读取字符区域哈希或红色关闭按钮的质心，未对主要显示 Canvas 调用 `getImageData()`。
读取发生在本次计时终点之后，但会影响后续输入与更新；不能从延迟中机械扣除。
4K／1080p 的读取中位耗时分别为：打字约 2.1／1.5 ms，滚动 11.5／5.5 ms，拖窗 14.0／6.4 ms。
因此拖窗收益中也可能包含分辨率下降对测量开销的影响。

所有正式统计的打字／滚动标记都观察到变化，没有负延迟；拖动按位置对应，未把合并或跳过的位置当作已响应。
早期试探批次 `typing-a`、`typing-b`、`typing-c` 存在切换后未完整重绘问题，**不进入上述统计**；
修复刷新过程后重新采集了 `typing-clean-a/b/c`。
测试临时文档已关闭并丢弃，原有文档未编辑。

本地诊断输出在忽略的 `test-results/` 目录，均不进入 ZIP 分发包：

- `transmission-scale-*.json`：消息、实际尺寸和矩形范围；`1080p-mac-physical-display.png`：只含系统版本和显示器信息的截图区域。
- `interaction-1080-typing-clean-a/c.json`、`interaction-4k-typing-clean-b.json` 及各自 `-summary.json`。
- `interaction-1080-scroll-a/c.json`、`interaction-4k-scroll-b.json` 及汇总。
- `drag-1080-drag-a/c.json`、`drag-4k-drag-b.json` 及汇总。
- `transmission-latency-summary.json`：上表合并计算结果。

统计采用排序中间索引计算 p50、最近秩计算 p95，样本规模有限。
协议探测入口为 `node scripts/transmission-scale-probe.mjs baseline|1|0.5`，仅对已由用户认证的客户端执行，
不读取凭据。此脚本属于实验诊断，不替代产品内完整的缩放、全刷和鼠标处理流程。
